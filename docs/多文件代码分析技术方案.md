# 多文件代码分析技术方案

编制日期：2026-10-22。

状态：待实施。本文件汇总本次讨论确定的需求、技术设计、契约与实施顺序，不代表现有代码已经具备这些能力。本轮仅新增方案文档；实际实现时按阶段更新 [现有架构说明](./architecture.md) 和 [产品范围](./product.md)。

## 1. 目标与首版边界

用户上传多个代码文件后直接点击生成，不需要选择或描述入口。系统分析全部上传内容，连接有明确依据的执行关系，将互不关联的函数、事件或任务保留为独立流程，最终支持从节点定位到对应文件的原始代码。

首版确定以下边界：

- 默认本次上传的源码为同一种语言。程序调用 Jev 统一识别一次，后续所有文件分析复用该结果；不做逐文件分类和混合语言纠错。
- Jev 只负责语言识别。代码语义、执行单元、控制流及跨文件关系由生成模型理解，不能将两者混称为语言理解。
- 不要求用户提供入口，不设置入口发现 Agent，不把不同入口串成虚假的顺序流程。
- 用户负责选择目标相关文件；系统允许存在独立文件和缺失依赖，不强制所有文件连通。
- 使用简单 RAG：精确查找、关键词检索和向量检索。暂不使用 Graph RAG、图数据库、社区摘要或沿知识图谱扩展。
- 不读取任意本机目录、不执行上传代码、不安装上传项目依赖，不支持压缩包和仓库导入。
- 语言解析器不是前置条件，不把能力限制为 JS/TS；后续可以用解析器增强索引质量。
- 保留现有单文件接口和历史会话，新能力使用版本化契约。

## 2. 完整处理流程

1. 前端批量读取文本文件，展示文件名、相对路径和大小；用户确认后上传。
2. 后端校验文件、路径和总大小，保存原始文本并创建不可变快照。
3. 程序选取代表源码调用 Jev，将统一语言及检测状态绑定快照。
4. 程序扫描文本，建立文件目录、行偏移和代码块索引；准备关键词与向量检索。
5. 根据缓存安排文件分析任务。Worker 分批阅读全部上传源码，返回结构化文件语义索引，不生成最终图。
6. 程序合并索引，检查覆盖范围，查找导入、调用和注册关系的候选目标。
7. 对歧义关系使用 RAG 查找候选，通过只读工具定点读取相关源码；确有必要时调用关系核对 Worker。
8. 系统整理执行单元和经过核对的关联，独立单元照常保留；按上下文预算组织生成任务。
9. 为生成任务构建索引、必要原始代码和证据组成的上下文，生成局部结构化流程。
10. 程序统一分配节点 ID，合并局部流程，加入明确标记的调用或触发关联，生成最终图源和跨文件 mappings。
11. 校验结构、节点覆盖、源码范围和关系证据；失败回到对应阶段，携带反馈重试。
12. 全部必需任务完成后提交最终结果，前端展示流程图；点击节点切换文件并高亮对应范围。

所有上传文件都必须进入覆盖检查。RAG 用于寻找实现和补充上下文，不能用检索排名决定哪些上传文件可以不分析。达到预算时返回未完成状态，不把遗漏文件的结果标记为完整成功。

## 3. 相比现有实现的变化

当前链路以单个 `code` 字符串为中心，模型直接提交 `mermaid + mappings`，没有文件基础索引和语义索引。三类数据的职责如下：

| 数据     | 回答的问题                           | 建立方式                             |
| -------- | ------------------------------------ | ------------------------------------ |
| 基础索引 | 源码在哪，如何准确读取               | 程序处理文本，不理解代码             |
| 语义索引 | 文件与执行单元做什么，有哪些引用线索 | 模型首次阅读并结构化提取             |
| mappings | 最终图节点对应哪段原始源码           | 生成阶段给出范围，程序校验与补齐身份 |

首次建立可靠语义索引仍需覆盖源码，不能承诺免除第一次阅读成本。节省来自缓存复用、精简索引、定点补读和分组生成，避免多个阶段反复输入全部文件。

## 4. 新增技术与职责边界

| 能力           | 技术决策                                                                               |
| -------------- | -------------------------------------------------------------------------------------- |
| 工作流         | 复用 LangGraph `StateGraph`，不另建手写状态机                                          |
| 并行任务       | `Send` 分发文件 Worker，分批执行并设置进程级模型并发限制                               |
| 模型调用       | `createAgent`、`toolStrategy`、Zod；SDK 重试关闭，图统一控制                           |
| 快照和去重     | Node `crypto` 的 SHA-256，原始正文按内容哈希去重                                       |
| 索引和任务存储 | SQLite，沿用官方 saver 暴露连接的业务 repository 模式                                  |
| 关键词检索     | SQLite FTS5 / BM25，加路径、标识符精确匹配                                             |
| 语义检索       | 独立 Embedding 接口，使用现有 `@langchain/openai` 中的 `OpenAIEmbeddings` 适配兼容服务 |
| 向量查询       | SQLite BLOB 保存向量；受限规模内应用侧余弦精确检索                                     |
| 文本工具       | 四个只读业务工具，共享快照访问、限额和证据生成逻辑                                     |

controller 只处理参数、HTTP/SSE 和请求取消；service 管理请求生命周期、互斥、观测和资源；graph 管理调度、条件边和重试；chain 封装单个模型角色；repository 管理存储；工具通过 service 读取快照，不直接访问任意路径。

不额外引入多智能体 SDK、图数据库或独立向量服务。Embedding 服务并不等同于现有生成服务，必须独立配置和验证。

## 5. 快照、路径和原始位置

下列 TypeScript 为领域结构示意；实施时所有跨边界结构均以完整 Zod schema 为真源并推导类型，`SourceRange`、证据和诊断等公共结构统一定义，不直接复制示意代码作为未经校验的接口。

### 5.1 身份与数据

首版沿用会话作为所有者，不新增项目管理功能。

```ts
interface SourceSnapshot {
  snapshotId: string
  sessionId: string
  manifestHash: string
  files: SnapshotFile[]
  languageDetection: LanguageDetection | null
}

interface SnapshotFile {
  fileId: string
  path: string
  contentHash: string
  byteSize: number
  lineCount: number
}
```

`manifestHash` 根据排序后的路径与内容哈希计算；文件新增、删除、修改或重命名都会改变快照。`fileId` 由服务端分配，不由模型猜测。`analysisId` 标识一次执行，使用同一快照重新生成也有新的分析 ID。

### 5.2 上传与路径

- 首版用 JSON 上传 `{ files: [{ path, content }] }`，不新增 multipart 依赖。
- 路径统一为 `/` 分隔的项目内相对路径；拒绝绝对路径、盘符、NUL、`..` 越界和规范化后的重复路径。
- 普通多文件选择通常只有文件名，不能假装已经取得原目录结构。预览区允许调整相对路径；缺失信息时保留引用歧义。
- 扩展名只用于文本过滤、展示和高亮提示，不作为最终语言分类依据。
- 前端严格解码为 UTF-8，遇到无效编码、二进制、空文件或限制超出时给出文件级错误，不静默跳过。
- 初始限制为最多 20 个文件、单文件 200 KiB、总源码 2 MiB。它们是资源边界，不是语义质量或模型预算保证。
- 新上传接口单独配置 16 MiB JSON 请求体上限以容纳转义开销；不得仅放宽现有全局中间件而取消业务校验。按原始文本 UTF-8 字节数检查实际源码大小。

### 5.3 位置规范

保存原始 CRLF / LF、BOM 和缩进，不通过替换换行后再计算行号。建立行起始偏移表；行列从 1 开始，列按 UTF-16 code unit 计数，范围终点列采用排他语义，与编辑器选择一致。

内部统一使用原始文本的半开区间 `[startOffset, endOffset)`，转换为行列用于接口。覆盖统计也使用偏移区间，避免长单行被切成多个块后仅按行数误判已完整阅读。

## 6. Jev 识别时机

快照创建成功后、语义索引与语言规则选择之前，由程序直接调用现有 `runDetectLanguage`。基础文本扫描可以在同阶段完成，但模型分析必须等待检测结束。

代表源码选择规则：

1. 在非空文本文件中按有效文本量排序，使用最长候选，路径作为稳定排序的次级键；不使用特定语言注释语法过滤。
2. 候选较小时使用全文；较大时取首、中、尾的完整行样本，保留各段来源信息，总采样字符数设上限。
3. 初始采样上限建议 16,000 个 UTF-16 code unit，长单行按文本范围截取并明确标记为片段。
4. 同批源码同语言属于产品输入假设。该采样不证明每个文件都同语言，也不因不同扩展名额外调用 Jev。

检测结果写入快照并在主图状态引用。文件 Worker、生成、重试及追问均复用，不向智能体注册检测工具；模型不得覆盖语言。低置信度或临时失败保留 `unknown`，使用通用规则；配置和鉴权错误沿用现有失败策略。

默认同一快照只尝试识别一次，包括降级结果；对重新上传形成的新快照重新识别。不能在生成重试中偷偷触发检测。

## 7. 基础索引：纯程序处理

基础索引保存文件路径、正文哈希、行偏移、块范围和检索字段，不推断函数边界。

```ts
interface CodeChunk {
  chunkId: string
  fileId: string
  contentHash: string
  startOffset: number
  endOffset: number
  lineStart: number
  lineEnd: number
  chunkerVersion: string
}
```

初始分块参数：目标 120 行、重叠 20 行、单块最多 8,000 个 UTF-16 code unit。在上限内优先靠近空行切分；超长行使用偏移切分，正确映射原始列号，不切断代理对。所有块区间合并后必须覆盖文件正文。

正文不重复存进每条索引记录，读取时从内容哈希对应的正文切片。索引中的文本摘要或搜索字段与原始位置独立，禁止用预处理后的检索文本计算 mappings。

基础索引先于模型建立，因此没有语义索引时，搜索和读源码工具仍然可以工作。

## 8. 文件语义索引：模型阅读后提取

```ts
interface FileSemanticIndex {
  fileId: string
  summary: string
  units: ExecutionUnitIndex[]
  references: ReferenceIndex[]
  unresolvedItems: UnresolvedItem[]
  analyzedRanges: OffsetRange[]
  status: 'partial' | 'complete'
  schemaVersion: string
}

interface ExecutionUnitIndex {
  unitId: string
  name?: string
  scope?: string
  kind:
    | 'function'
    | 'method'
    | 'top-level'
    | 'event'
    | 'lifecycle'
    | 'reactive'
    | 'declaration'
    | 'other'
  range: SourceRange
  signature?: string
  summary: string
  controlRanges: ControlRange[]
  callSites: CallSite[]
  evidenceIds: string[]
}
```

`SourceRange` 包含 `fileId`、原始偏移和行列信息；`CallSite` 包含调用文本、位置、接收者或限定名、目标线索及引用证据。`ReferenceIndex` 记录导入路径、名称、别名、导出、注册等线索，不宣称已证明目标。

索引要求：

- 文件职责、单元职责简短，按字段长度和数组大小设置 Zod 上限，不返回内部推理。
- 保留关键分支、循环、异常和返回的源码位置，不在索引中复制长段正文。
- 纯声明或配置也必须登记，可说明无独立执行流程；不能为了覆盖而制造执行节点。
- 模型先返回任务内临时单元 ID，程序校验范围后分配正式 ID。重叠块结果按范围、作用域与名称合并，不能只按函数名去重。
- 跨块单元输出片段与待补全状态；通过相邻块或定点读取补齐后再确认边界。仍无法确定时明确保留未完整解析，不能编造结束位置。
- 嵌套函数分别记录作用域；位置重叠不等于重复单元。

首次建索引时由程序直接提供分配好的源码块和证据，不强制模型先调用 `read_code` 获取已知任务输入。小文件一次处理，大文件分块处理；合并节点只看结构化事实，必要冲突才补读原文。

完整索引要求全部正文已分配给成功提交且校验通过的任务、跨块缺口已处理。程序能证明处理覆盖，不能据此证明模型识别了每个语义细节；该质量必须另行评估。

## 9. 四个只读业务工具

所有工具使用 Zod 校验入参；`snapshotId`、会话所有者和预算从运行上下文注入，模型不能修改。返回结构包含数据、证据、截断状态和读取计量。页码或游标必须由服务端校验。

| 工具             | 入参概要                                      | 返回内容                                          |
| ---------------- | --------------------------------------------- | ------------------------------------------------- |
| `list_files`     | `cursor?`、`limit?`                           | 文件 ID、路径、行数、统一语言、索引状态，不含正文 |
| `get_file_index` | `fileIds`、`unitIds?`、`sections?`、`cursor?` | 指定文件/单元索引，默认只返回简短概览             |
| `search_code`    | `query`、`mode`、`fileIds?`、`limit?`         | 候选块 ID、位置、短片段、检索来源和排名           |
| `read_code`      | `selectors`                                   | 按块、单元或原始范围批量返回正文                  |

`read_code.selectors` 为判别联合数组：

```ts
type ReadSelector =
  | { type: 'chunk'; chunkId: string }
  | { type: 'unit'; unitId: string }
  | { type: 'range'; fileId: string; range: LineColumnRange }
```

单次选择器最多 8 个，默认最多返回 200 行且不超过 12,000 个 UTF-16 code unit；长单行仍受字符限制。搜索默认返回前 8 项，每项片段不超过 400 个字符；目录和索引默认分页 20 项。具体计数规则和上限必须写进工具说明。

截断时返回实际范围、`truncated: true` 和 `nextRange` / 游标，不能让模型误认为读到了完整单元。模型必须主动继续读取，已登记的失败或截断不计入完整覆盖。

每次原文输出由程序生成 `evidenceId`，绑定快照、内容哈希和实际范围。首次直接提供给 Worker 的正文也按同一方式登记。索引事实和关联必须引用当前任务可访问的合法证据。

工具不负责创建索引、写数据库、执行代码、识别语言或重试。结构化提交由各角色的 `toolStrategy` 提供，属于输出协议，不计入四个业务读取工具。

### 9.1 各角色的工具绑定

- 文件索引 Worker：默认仅绑定 `read_code`，需要邻近上下文时补读；不允许自己调度其他文件 Worker。
- 关系核对 Worker：绑定全部四个工具，但程序先提供已知索引和调用证据，避免无效的目录往返。
- 最终生成 chain：首版使用预先构建的证据包，不绑定自由搜索工具，保持一次生成尝试一次模型调用。
- 后续追问：可绑定索引、搜索和读取工具，但只能访问生成结果绑定的快照。

## 10. 简单 RAG 实现

### 10.1 检索通道

1. 路径、符号全名、导入名称优先走精确查找。
2. 关键词使用 FTS5 / BM25，搜索字段包含路径、原始标识符、驼峰/下划线拆分词、已有职责摘要和代码块文本。
3. 语义查询调用 Embedding，再做余弦相似度检索；向量输入为路径和原始代码块，已有符号信息可以增补，但不得为每个块额外调用生成模型写摘要。
4. 关键词和向量各取前 20，通过 RRF 融合并按原始位置去重；精确匹配结果优先，融合后默认返回前 8 项。
5. RRF 使用 `sum(1 / (60 + rank))`，避免直接相加尺度不同的 BM25 与余弦分数。SQLite BM25 排序方向要按官方行为处理。

FTS5 默认分词不能可靠覆盖所有中文短词、路径符号和短标识符。对这些查询提供参数化精确/子串匹配补充；`MATCH` 表达式由程序转义构造，不直接执行模型提供的检索语法。

RAG 只检索当前快照内的上传内容，不读取未上传依赖，不沿关系图遍历。相似度只能用于候选召回，不能成为连接调用边的证据。

### 10.2 向量存储与降级

- 使用固定格式的 Float32 向量，保存维度、模型标识和输入构造版本，查询前校验一致性及数值有效性。
- 首版设置最多 2,000 个活动代码块的精确向量查询上限，超出时跳过向量通道并提示降级；不是只分析前 2,000 块。
- 查询范围先按快照和文件筛选；缓存活动向量，避免每次从 SQLite 重读全部 BLOB。CPU 计算需限制并发并分批让出事件循环。
- 启动时检查 FTS5 能力和 Embedding 配置；缺失 FTS5 可退回受限文本匹配，Embedding 超时或未配置可退回关键词。降级状态写入诊断，不伪称混合检索成功。
- Embedding 请求支持批量和输入上限，按文本块哈希缓存。代码会发送给配置的 Embedding 服务，行为与源码分析同样纳入数据使用说明和用量观测。
- 未取得凭据和模型名之前不预设某个端点有向量能力；实施时用中文功能描述、英文标识符和代码片段评估后固定部署配置。

## 11. 智能体、状态图与预算

### 11.1 角色

采用固定分工，不额外创建自由决策的总控 Agent：文件 Worker 建索引，关系核对 Worker 处理歧义，最终 chain 生成局部流程。任务规划、合并、条件判断和终止均由程序节点完成。

主图按以下顺序执行：

```text
prepareAnalysis → detectLanguage → buildBasicIndex
  → planIndexBatch → indexFile × N → mergeIndexes
  → resolveReferences → verifyBatch（需要时）→ assessCoverage
  → buildGenerationTasks → generateUnit × N → validateUnit
  → composeResult → validateResult → 完成
```

`assessCoverage` 根据缺失范围和关系诊断返回相应补充节点；`validateUnit` 与 `validateResult` 根据错误类型返回生成或核对阶段。全部使用原生图条件边，不另建 provider 分支。

### 11.2 并发与持久化

- 初始文件 Worker 并发 3；每批最多发出 3 个 `Send`。另有进程级共享信号量，防止多个会话相乘突破供应商限制。
- 并行输出使用按 `taskId` 合并的 reducer，避免竞争覆盖。冲突记录由串行合并节点处理。
- Worker 不互相对话、不共享长聊天历史；只传递简短结构化事实与证据引用。
- 主状态引用 `snapshotId`、`analysisId`、检测结果、任务 ID、覆盖摘要、预算和最终结果，正文存业务表，不在每个 checkpoint 中重复复制整个项目。
- 使用官方 checkpointer 持久化主图；Worker 为调用级上下文，任务成功结果幂等写入业务表。恢复先检查任务记录，不重复提交已完成结果。
- 不承诺供应商模型调用恰好一次：模型成功但本地提交前崩溃时仍可能重发；记录该边界并依赖缓存减少重复。

### 11.3 预算

初始开发值：单 Worker 最多 4 次模型调用；每任务校验重试沿用 `CODE2FLOW_MAX_RETRIES`，初始 1 次；每次分析最多 120 次模型调用、600,000 输入 token、80,000 输出 token、15 分钟。它们是可调资源保护值，不是容量或效果承诺。

为最终生成预留至少 20% 的总输入预算，不让索引和探索耗尽全部额度。供应商上下文窗口必须通过配置给出；每次调用满足“系统规则 + 工具定义 + 消息 + 预期输出 + 安全余量”不超过该窗口。

有适用 tokenizer 时使用它；否则按保守文本长度估算并明确标记估算，实际计费用供应商 usage。上下文过长错误触发更小任务，不无条件原样重试。工具返回字符限额不能冒充精确 token 限额。

索引补读、关系补充与校验重试独立计数，仍受总预算约束。达到限额时停止调度新任务，保留可复用索引，返回具体缺失范围；完整成功前不发送 `done`。

## 12. 跨文件关联与独立流程

首版只保存轻量关联表，不构建 Graph RAG。

```ts
interface CrossFileReference {
  referenceId: string
  sourceUnitId: string
  callSiteId?: string
  targetUnitId?: string
  targetHint?: string
  kind: 'call' | 'import' | 'registration' | 'request'
  status: 'resolved' | 'inferred' | 'unresolved'
  evidenceIds: string[]
  diagnostic?: string
}
```

程序先根据路径、导入别名、限定名和作用域查候选，再验证证据。只依赖名称相同或向量相似时不得标记为 `resolved`。模型自报高置信度也不能绕过这些规则。

| 情况                             | 最终处理                                 |
| -------------------------------- | ---------------------------------------- |
| 调用位置和唯一目标有明确证据     | 建立调用关联                             |
| 只有 import，没有执行调用        | 记录依赖，不画成执行顺序                 |
| 事件/路由注册绑定处理函数        | 建立带类型的注册或触发关联               |
| 多个同名候选、动态方法目标不确定 | 保留未解析，不强行连接                   |
| 被调用实现未上传                 | 在原调用节点说明外部边界，不补写内部流程 |
| 只有相同业务词汇                 | 保持独立                                 |

`resolved` 仅表示当前源码范围内目标关联有依据，不证明运行时必定发生。跨服务请求不能只按 URL 字符串相同就等同本地函数调用，缺少方法、基地址或注册配置时保留不确定性。

循环依赖、递归和互相调用按单元 ID 去重，单元只分析和生成一次，关联可以回指已存在单元；不递归展开到无限深度。Vue 事件、watch、computed 和生命周期保留不同触发语义。

## 13. 分组生成、节点身份与最终契约

### 13.1 为什么新增局部流程中间结构

多次生成若直接拼接 Mermaid 字符串，会出现同名 ID、重复头部、错误替换和跨文件返回路径混接。新链路保留现有 chain 的职责、Prompt 粒度规则和结构化提交方式，但新增 v2 局部流程 schema，由程序确定性合并与序列化；旧 `FlowDraftSchema` 和旧接口保持原样。

该结构仅为模型输出的合并契约，不是额外实现完整静态控制流分析器。

```ts
interface UnitFlowDraft {
  unitId: string
  nodes: Array<{
    localId: string
    kind: NodeKind
    label: string
    description: string
    range: SourceRange
    evidenceIds: string[]
    callSiteIds?: string[]
  }>
  edges: Array<{
    from: string
    to: string
    label?: string
  }>
  entryLocalId: string | null
}
```

所有节点范围属于该执行单元所在文件；局部边只能引用本任务节点。纯声明单元可返回空节点并说明原因，不能捏造起止位置。嵌套单元只描述定义/注册行为，具体函数体归该嵌套单元生成，避免重复展开。

### 13.2 证据包与规模控制

每个生成任务包含目标单元索引、必要完整源码或经核对的连续子范围、相关类型/常量、调用证据和未确定项。RAG 优先帮助补齐目标，关键控制流不能因相似度排名低而被删掉。

一个请求能容纳的多个小单元可以批量生成，减少系统提示重复。超大单元优先补齐分段索引并进行带显式连接端口的分段任务；如果无法在预算内核对分段间控制关系，返回该范围超限，不把各段随意顺序连接。首版不以“只给摘要”作为超限补救。

### 13.3 程序合并规则

- 按文件、单元、原始行号和局部节点的稳定顺序分配 ID，例如 `n_action_12_f02_u03_1`，保留 `n_<kind>_<lineStart>` 前缀约定。
- 从节点结构推导 mappings，增加 `fileId`、`unitId` 和合法证据引用。一个节点对应一个文件内的连续源码范围。
- 局部控制边保持实线；已确认调用使用独立样式及“调用”标签连接调用节点与目标入口，避免误解为函数体返回后继续沿目标出口执行。
- 不自动从被调用单元末尾向所有调用者后继连线。该关系不是完整跨过程执行模拟。
- 同一目标多处调用时保留每个调用点，共享目标单元，不因共享而混合返回路径。
- 推断或未解析项默认在节点说明和诊断中呈现，不以确定执行边连接。
- 用已确认调用/触发关系分组，独立单元保留独立子图；共享工具函数可以关联多个执行入口，但不得新增统一起点强行串行化。
- 文件/单元容器只作为展示分组，不作为执行节点，不伪造源码 mappings。没有源码的“未知实现”也不创建带假行号的节点。
- 转义所有标签和边文本，只序列化受控节点形状及连线；禁止模型注入点击脚本、任意 Mermaid 指令或 URL。

### 13.4 对外结果

```ts
interface MultiFileFlowResult {
  version: 2
  snapshotId: string
  analysisId: string
  detectedLanguage: SupportedLanguage
  hasExecutableFlow: boolean
  mermaid: string
  mappings: MultiFileNodeMapping[]
  diagnostics: PublicDiagnostic[]
  coverage: PublicCoverage
}
```

最终结果仍是一个包含相关连线与独立子图的流程图。新增中间结构属于后端内部实现，不在用户操作流程中暴露。

如果全部上传内容只有声明、注释或配置且没有可展示的执行流程，返回 `hasExecutableFlow: false`、空 mappings 和明确说明；前端展示普通空态，不解析空图源，不创建带虚假行号的提示节点。该情况与分析未覆盖完成的失败状态分开处理。

## 14. 校验、失败和取消

校验必须包括：Zod 结构、节点 ID 唯一性、节点与 mappings 双向对应、标签一致、边端点存在、文件/范围合法、证据可访问、调用关联目标有效、上传内容覆盖情况以及最终图源实际解析。

不再用“夹到合法行号/附近执行行”掩盖模型越界。v2 先严格校验范围，再做不改变身份的有限展示处理；旧归一化行为留给旧接口，分别测试。

后端不为解析校验启动浏览器服务；对程序生成的受控图源做结构和序列化检查，前端使用已有 Mermaid parser 实际解析并渲染，失败保持错误状态、节点定位不可用，并提供一次明确的重新生成入口。测试环境通过前端解析测试验证真实兼容性，不能把后端轻量规则称为完整 Mermaid 解析。

| 失败类型                 | 处理                                       |
| ------------------------ | ------------------------------------------ |
| 索引结构或源码范围错误   | 向原文件任务反馈，图控制重试               |
| 目标冲突                 | 进入关联核对；仍不确定则保留诊断           |
| 局部流程结构、控制边错误 | 重试该生成任务，不重建全量索引             |
| 生成发现索引缺口         | 有界返回补读/核对节点，计入总预算          |
| 配置、鉴权或输入错误     | 明确失败，不无意义重试                     |
| 总预算或必需覆盖未完成   | 不提交完整结果，显示缺失范围，缓存成功索引 |
| 未上传依赖或动态目标     | 可以成功，但必须带边界/未解析说明          |

断开连接或用户取消时传播 `AbortSignal`，停止后续调度并尽量取消进行中请求；迟到结果不得覆盖新分析。已完成且校验通过的索引可缓存，最终结果仅在当前 `analysisId` 且所有必需任务成功后提交。

不新增轮询式后台队列。进程重启不会自动继续发起模型付费请求；用户再次生成时，主图与任务记录检查完成项、复用缓存，再安排剩余工作。

## 15. 接口、会话与前端接入

### 15.1 v2 接口

| 接口                                                           | 用途                                                      |
| -------------------------------------------------------------- | --------------------------------------------------------- |
| `POST /api/v2/sessions/:id/snapshots`                          | 接收文件集合并创建不可变快照，返回清单及快照 ID           |
| `GET /api/v2/sessions/:id/snapshots/:snapshotId`               | 恢复快照文件清单及统一语言                                |
| `GET /api/v2/sessions/:id/snapshots/:snapshotId/files/:fileId` | 按需取得原始正文，用于编辑和定位                          |
| `PATCH /api/v2/sessions/:id/draft`                             | 保存多文件草稿及活动文件，使用 revision 乐观检查          |
| `POST /api/v2/generate-flow`                                   | `{ thread_id, snapshotId }`，执行并通过 SSE 返回结果      |
| `POST /api/v2/follow-up`                                       | `{ thread_id, snapshotId, question }`，基于已生成快照追问 |

客户端在一次“生成”动作中自动先创建快照再打开生成 SSE，无需用户额外操作。新快照操作不隐式把未分析文件标为成功。`analysisId` 在生成开始时由服务端分配，通过 metadata 交付；取消使用该 fetch 的中止信号。

快照和文件接口都校验所属会话，客户端不能只凭任意 fileId 访问其他快照。读索引工具不直接对外暴露为任意检索 API。

### 15.2 SSE 兼容

旧 `/api/generate-flow` 的事件名称和载荷完全保持不变。v2 仍使用 `metadata / mermaid / mappings / done / error`，仅在 v2 metadata 中增加 `version`、快照/分析 ID、阶段、完成计数、检索降级和覆盖摘要。

索引和检索阶段通过 metadata 展示进度，不发送伪造流程图。局部结构化草稿不作为完整图源发给旧解析器；v2 可在已校验单元合并后节流发送完整预览快照，最终 mappings 通过校验后交付。`done` 仅表示最终结果已持久化且服务端检查通过；客户端还需通过实际解析才进入可定位的完成状态。error 为终止事件，缺少 done 的断流不能显示成功。

### 15.3 草稿、恢复和定位

- 多文件草稿与分析快照分离，生成期间锁定编辑和会话切换，沿用现有请求互斥。
- 同一会话的生成、追问、草稿写入、快照变更和删除共用锁；不同会话可并行。
- 新生成清空旧结果和问答，失败也不恢复成旧图成功状态。
- 旧详情契约保持不变；为 v2 详情增加版本化适配，恢复文件清单、活动文件、sourceSnapshotId、结果和问答。旧单文件可在内部适配为一个虚拟文件，但不改写原有 checkpoint。
- 任意草稿文件、路径或清单与生成快照不同，禁用当前草稿定位和追问并提示重新生成。仅切换活动文件不算源码变化。
- 节点点击后按 `fileId` 切换 Monaco 文档，等待 model 就绪后滚动和高亮；文档身份包含会话、快照/草稿身份和文件 ID，保存每个文件的视图状态并在删除时释放 model。
- 追问从同一快照检索，不混入最新草稿，也不重新调用 Jev。

## 16. SQLite 表、缓存与清理

| 建议表                                             | 内容                                      |
| -------------------------------------------------- | ----------------------------------------- |
| `code_flow_source_blobs`                           | 内容哈希、原始正文、字节数                |
| `code_flow_snapshots` / `code_flow_snapshot_files` | 会话、文件成员、路径、语言检测及 manifest |
| `code_flow_chunks` / FTS5 表                       | 块位置、版本和可检索字段                  |
| `code_flow_file_indexes` / `code_flow_units`       | 经校验语义事实、单元及覆盖范围            |
| `code_flow_references`                             | 当前快照的轻量关联、状态和证据            |
| `code_flow_embeddings`                             | 输入哈希、模型、维度、格式版本、向量      |
| `code_flow_analysis_tasks`                         | 任务身份、状态、尝试次数、结果引用和诊断  |
| `code_flow_workspace_drafts`                       | 多文件草稿、revision 和活动文件           |

使用业务 migration 版本表管理建表与升级，在事务中完成 schema 变更；不手动读写官方 saver 内部表。批量结果短事务提交，不在网络调用期间持有数据库事务。

缓存分层：

- 基础分块：内容哈希 + 分块规则版本。
- 本文件语义：会话范围 + 内容哈希 + 检测语言 + Prompt/schema/模型配置版本。
- 若模型输入带路径、导入上下文或其他文件信息，这些实际上下文也必须计入缓存键；不能错误复用位置相关结论。
- 语义缓存保存可重绑定的本文件偏移与临时身份，命中后重新校验并绑定本快照 fileId；不复制旧 evidenceId。
- 跨文件关联：快照 manifest + 相关配置 + 关联规则/Prompt 版本，重命名、导出变化和依赖删除都需重算。
- Embedding：实际嵌入文本哈希 + 模型标识/维度 + 输入构造版本；不同向量空间不能混用。

删除会话时沿用官方 `deleteThread` 和删除标记，清理该会话草稿、索引、任务和快照引用；按引用计数清理无引用正文与向量。不能仅删目录元信息而把用户源码长期遗留在索引表。

## 17. Token、观测和配置

### 17.1 降低重复输入

- 默认先索引后精读，不把所有文件索引、源码和工具绑定给每个角色。
- 首次索引直接投递已知源码，后续按工具位置读取；同一上下文按偏移去重并合并相邻范围。
- 共享缓存只表示已有事实，不表示当前模型已经看到正文。最终生成需要的证据仍必须实际进入其上下文。
- 工具历史接近预算时结束当前任务，以已校验事实和必要原文启动有界后续任务，不不断追加长历史。
- 局部生成成功即缓存；重试只修复失败任务，避免重做语言检测与全量语义索引。
- 首版先采用一致的索引流程，保留“直接全量输入”作为离线对照；小文件快捷路径在评估证明收益后再加，避免新增不可控路由。

### 17.2 用量与日志

分别记录 Jev、索引、关联核对、生成、追问和 Embedding 的调用/用量。旧 usage 页面若仍只统计生成，应显式标明范围；v2 展示模型分析总用量时不能把索引成本漏掉，也不能把 Embedding token 与生成 token 混称。

记录重复读取比例、工具返回量、缓存命中率、覆盖情况、阶段耗时、实际/估算 usage 和降级状态。关闭源码及完整 agent output 的调试打印，尤其要处理当前 chain 的输入消息与输出日志；仅记录 ID、长度、状态和经过白名单处理的诊断，不记录正文、密钥或内部推理。

### 17.3 实施时新增的配置

## 18. 代码落点与实施顺序

建议新增 `backend/src/domain/source/` 和 `domain/multifile/` 契约；`services/` 增加 snapshot、index、retrieval、reference-resolution 和 context-builder；`repositories/` 增加相应 SQLite 实现；`ai/chains/` 增加文件索引、关系核对和局部流程 chain；`ai/tools/` 放四个只读工具；`ai/graph/` 放 v2 编排；`utils/` 放位置、分块、受控序列化和严格范围校验。

- [ ] 阶段一：v2 快照、路径和原始位置契约；实现上传、存储、业务 migration 与旧接口兼容。验证多文件输入不会丢失路径和行号。
- [ ] 阶段二：基础分块、FTS5、Embedding 适配与降级；实现四个工具及快照访问限制。验证没有语义索引时仍能检索和读取。
- [ ] 阶段三：统一 Jev 检测、文件语义索引、覆盖检查和缓存重绑定。验证首次全覆盖、重复分析命中缓存、unknown 不被模型改写。
- [ ] 阶段四：LangGraph 并行任务、关联解析与歧义核对、预算和取消。验证同名目标、循环依赖、断流和失败任务不会污染结果。
- [ ] 阶段五：局部流程 schema、证据包、合并与跨文件 mappings；接入 v2 SSE、文件切换和快照追问。验证相关流程连通、独立流程保留、节点定位正确。

## 19. 验收与测试

| 编号 | 触发条件                                     | 必须满足的结果                                                          |
| ---- | -------------------------------------------- | ----------------------------------------------------------------------- |
| A1   | 上传多个同语言文件并生成                     | 无需入口，所有文件进入覆盖记录，独立执行单元不会消失                    |
| A2   | 首次分析、局部重试、追问                     | 每快照 Jev 只识别一次，后续复用，unknown 保持一致                       |
| A3   | CRLF、BOM、中文、emoji、长单行与分块重叠     | 原始偏移、行列、读取范围和最终定位一致                                  |
| A4   | 同名函数、导入别名、缺少目录、动态目标       | 不按名称或相似度误连，歧义公开保留                                      |
| A5   | 相互调用、递归、共享函数、独立任务           | 有限分析，不复制无限子流程，不自动混接返回路径                          |
| A6   | 相同内容重复生成或文件改名                   | 正确复用本地事实并重绑定身份，跨文件关系按需失效                        |
| A7   | 工具截断、索引分块失败、预算超限             | 缺失范围可见，不将部分覆盖标为完整 done                                 |
| A8   | 缺少向量配置、向量维度变化、FTS5 不可用      | 明确降级或重建，不混用向量，不丢文件                                    |
| A9   | 多文件生成后编辑、切换会话、取消、刷新、删除 | 不混用快照，不受迟到响应覆盖，删除清理源码引用                          |
| A10  | 最终合并多个局部结果                         | ID 唯一、节点/mappings 双向覆盖、调用与局部控制边语义可区分，实际可解析 |
| A11  | 旧单文件接口和历史会话                       | 原事件载荷及追问、恢复行为不被 v2 改坏                                  |
| A12  | 对比全量输入与索引流程                       | 分别报告首次/缓存命中成本、关系与控制流准确率，不只报告图能渲染         |

后端测试放在 `backend/tests/`，覆盖 schema、读取工具、检索、分块、缓存、任务 reducer、预算、SSE 和 saver 兼容。使用本地兼容模型夹具测试 LangChain/StateGraph 真实集成，避免测试依赖在线密钥；Embedding 单独提供固定向量夹具。前端测试覆盖解析、事件版本、文件切换和范围转换。

实现阶段按改动范围执行根目录 `check` 及后端 `typecheck:tests`，具体命令以 package.json 为准。真实模型联调另验证 Jev 单次分类、多语言索引质量、Embedding 召回和端到端语义；没有真实联调不能宣称这些效果通过。本轮纯文档仅检查引用、内容一致性及差异，不运行业务测试。

## 20. 后续扩展边界

目录工具、用户描述具体流程、入口发现、按需只分析仓库部分内容、语言专用解析器、Graph RAG 和独立向量服务均为后续议题。当前只保留快照、检索、语义索引和生成之间的清晰接口，不提前实现这些功能。

后续目录模式只需替换文件获取与范围选择，复用本方案的工具、索引和生成证据机制；是否加入 Graph RAG，应由简单 RAG 的漏召回和成本数据决定。
