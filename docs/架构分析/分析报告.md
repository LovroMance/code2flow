# Code2Flow 全项目架构与功能链路分析

分析日期：2026-10-19。分析范围：当前工作区代码、根目录及双端配置、阶段规划、Prompt 与架构文档；基准分支 `master`，HEAD `b8dc663`。工作区已有未提交修改，本报告包含当前 `observability/`、`eval/` 等新增实现，不等同于仅分析 HEAD。

配套产物：[图表总览](./图表总览.html)（离线浏览、缩放、下载 SVG）、[Mermaid 源图](./diagrams/)、[源码索引](./源码索引.md)。原有 `docs/项目分析报告.md` 保留；本文独立核对代码后生成。

## 1. 核心判断

Code2Flow 是 npm workspaces 管理的前后端分离应用：Vue 单页前端承接代码编辑与可视化，Express 后端以 LangChain 工具调用生成结构化结果，通过 POST + SSE 推送 Mermaid，再以节点映射驱动 Monaco 定位。源码主要经 LLM 分析，没有确定性的 AST → CFG 编译管线，因此图和行号的语义正确性依赖模型与校验能力。

当前产品已经形成阶段一主闭环，并实现阶段二的最小追问和持久化上下文；不能据此认为完整多轮聊天、复杂 Vue 语义准确率或生产部署已经验收。

最重要的架构事实：

1. `graph` 是节点函数、状态对象、路由函数和 `while` 循环组成的手写状态机。仓库声明了 `@langchain/langgraph`，但 `backend/src` 没有导入它，也没有使用 `StateGraph`。本文的“graph”均指这套自研编排。
2. Agent 有 `langchain` 与 `graph` 两个 provider，代码默认值和 `.env.example` 都是 `langchain`。追问只支持 `graph`；不能把 graph 的重试、检查点能力泛化到所有运行方式。本文未读取本地密钥文件，实际启动时选中的 provider 需看运行环境。
3. 当前联动方向是“图节点 → 代码行”；没有看到“编辑器选中代码 → 图节点高亮”的反向实现。
4. SSE 推送的是逐次完整 Mermaid 快照，不是字符 delta；mappings 在最终结果时一次性下发，因此预览阶段节点通常还不能定位代码。
5. 新增观测与评估已进入服务调用路径，但它们记录的是部分程序化质量信号，不代表 Mermaid 真正解析成功或控制流语义已经被证明正确。

## 5. 核心链路：生成流程图

### 5.1 请求入口

`WorkspacePage` 按钮 → `useWorkspacePage.handleGenerate` → `useFlowGeneration.generateFlow` → `flow-stream.api.streamGenerateFlow`，发出 `{code, thread_id}`。控制器先用 Zod 验证；失败时 HTTP 400 JSON，成功后设置 SSE 响应头，再进入 service。

service 创建/接收 trace，注入默认文件 checkpointer；Agent 依据 `CODE2FLOW_AGENT_PROVIDER` 选路。`langchain` 直接调用 draft，跳过 graph 检查点、图节点重试与状态恢复；`graph` 进入下述状态流程。

### 5.2 graph 主流程

初始化请求状态 → 按 threadId 恢复 checkpoint → 判断 mode → detect-language → 保存 checkpoint → analyze-flow → validate → normalize 并保存结果，或 retry 后再次 analyze，超限则保存并抛错。

`maxRetries` 在初始 state 中默认 1，即最多 2 次分析尝试；不是阶段规划的“最多重试 3 次”。`CODE2FLOW_MAX_RETRIES` 被观测配置读取，但 API/service 未把它传给 graph input；修改环境变量可能只改变轨迹标记，没有改变线上实际重试上限。

重要边界：`generateCodeFlowDraft` 内部已经执行 schema 与 Mermaid 检查并可能抛异常；`analyzeFlowNode` 没有把这些异常转成 `state.error`。因此这些错误、模型网络错误会直接退出 graph，不经过 validate 后的 retry 条件边。当前自纠错主要覆盖成功返回 draft 后的节点校验失败，不能描述为“任何模型错误均自动重试”。图 06 同时画出正常流转和异常旁路。

### 5.3 工具调用能力层

`ChatOpenAI.bindTools` 绑定两个工具，`parallel_tool_calls=false`、`tool_choice=auto`。每轮聚合 `AIMessageChunk` 与 tool_call 参数：

- `detect_language`：忽略模型自行判断的语言，实际运行本地正则评分函数，并把结果作为 ToolMessage 返回。
- `submit_code_flow_result`：若尚未执行语言工具则返回工具错误，要求先识别；否则规范化 Mermaid，按 Zod 与 nodeId 规则解析，再归一化行号后返回。
- 未调用工具直接报错；未知工具返回 ToolMessage；4 轮内没有有效提交则失败。

graph 虽已预识别语言，chain 的 `hasDetectedLanguage` 仍从 false 开始，模型仍需走一次语言工具往返。这是两层各有约束所产生的重复，不是两次外部语言分类服务。

### 5.4 SSE 到界面

部分工具参数尚不是合法 JSON，抽取器扫描其中 `mermaid` 字符串，解码转义并丢弃未闭合的最后一行；通过轻量 Mermaid 检查且与上一快照不同才推送。最终控制器发送最终 metadata、mermaid、mappings、done；异常发送 error 并结束连接。

客户端按 `\n\n` 分帧、读取 `data: `、JSON.parse 后更新状态；每次 mermaid 都替换当前图源。渲染 composable 监听图源和 mappings，用 requestId 丢弃较旧的异步渲染结果，避免慢渲染覆盖新图。图 05 是生成时序；图 07 展示事件和前端状态。

## 6. 节点定位与数据契约

生成结果：`{detectedLanguage, mermaid, mappings}`。mapping 包含 `nodeId`、`kind`、`label`、`description`、`lineStart`、`lineEnd`，可选列号。kind 仅 `start / action / decision / return / end`；Vue 生命周期和 watch 没有专用 kind，靠标签和描述解释。

Prompt 推荐 `n_<kind>_<lineStart>` 并允许后缀；此格式未通过 schema 强制。行号进入 ID 也意味着代码插行可能改变 ID，不能承诺跨编辑稳定。

服务端对 mappings 做重复 nodeId 和“ID 字符串出现在 Mermaid 中”的检查，但没有解析图节点集合，因此不能严格证明它是实际节点定义，也没有反向验证每个图节点都存在 mapping。行号归一化会钳制到源码范围，避开空行、常见注释和独立括号，向后优先寻找可执行行；这是启发式修正，不能证明节点对应的真实语义，也不是完整语言解析器。

图节点定位链路为：追加 `click <nodeId> code2flowNodeClick` → Mermaid `bindFunctions` → 全局回调 → FlowDiagram emit → 页面查 mapping 并预填追问 → `CodeEditor.focusMapping` → 滚动、选区、整行/行侧装饰。图 08 展示此链路；图 10 展示数据关系。编辑代码后未自动清空结果，可能发生旧图映射新代码的错位。

## 7. 追问与持久化链路

前端生成成功、mappings 非空且没有进行中请求时启用追问；发送当前 thread_id、question 和当前编辑器 code。Agent 要求 provider=graph；初始化状态时读取同一个生成命名空间：`generate:<threadId>`。

当前 code 非空时优先使用新 code，同时从 checkpoint 恢复旧 result；追问节点将 code、question、Mermaid 和 mappings 交给普通模型 invoke，返回中文解释文本，覆盖 checkpoint 的 explanation，再以 JSON 响应。图 09 为追问时序。

文件检查点的作用是跨后端进程重启保留最后上下文；它不保存重试计数、完整对话消息或可恢复执行游标，不等价于 LangGraph 框架 checkpoint。文件实现使用进程内 cache + 串行写队列，适合单实例；并未提供跨进程锁、事务或原子替换。相同线程的并发请求也没有状态级互斥。

当前模型输入并未包含上次 explanation 或历史 question，因此“可连续追问同一张图”成立，“能理解上一轮聊天里的省略指代”尚无明确实现。代码改动后追问还有“新代码 + 旧图”的上下文错配。

## 8. 观测、评估与工程链路

service 的 `runWithTrace` 收口采集器生命周期，成功和失败都完成 trace；自带 collector 时由调用者管理落盘。默认 `CODE2FLOW_TRACE` 非 off 即启用，默认写 `.code2flow/traces/runs.jsonl`。落盘异常只告警，不影响主链路。

trace 保存 provider/model/temperature/maxRetries/promptVariant 的配置指纹、源码 hash/长度/行数、步骤耗时、工具调用轮次、供应商返回的 Token 用量、重试数和结果摘要；不重复保存完整源码和 Mermaid。完整源码仍在 checkpoint 中。`promptVariant` 只是分组标识，当前没有对应的 Prompt 模板切换实现。校验错误使用覆盖式字段，后续成功的 validate 会清空此前错误，因此不构成完整重试原因历史。

评估基线有 10 条 JS/TS/Vue 与边界样例，逐例调用真实 service，注入独立 trace，再检查结构、ID 一致性、行号范围、kind 覆盖、标签关键词、映射数量，共 6 类信号；默认并发 1。报告包含通过率、均分、耗时、LLM 轮数、Token 和重试率。A/B 根据配置和逐例分数产生比较 Markdown，是启发式对照，没有统计显著性计算。图 11 展示观测评估关系。

根目录 `dev/build/lint/typecheck/test/check` 聚合前后端脚本；后端另有 `eval / eval:ab / eval:traces`。没有发现 CI 工作流、容器编排或部署配置，阶段文档列出的 Vercel/Render 等属于部署方向。图 12 区分已实现的本地拓扑与部署建议。

## 9. API 与协议速查

| 接口                      | 入参                                 | 响应                                    | 主要边界                                            |
| ------------------------- | ------------------------------------ | --------------------------------------- | --------------------------------------------------- |
| `GET /api/health`         | 无                                   | JSON 健康状态                           | 表示 HTTP 服务可达，不验证模型端点可用              |
| `POST /api/generate-flow` | code 必填、thread_id 可选            | SSE                                     | 入参错误 HTTP 400；进入流后错误用 error 事件        |
| `POST /api/follow-up`     | thread_id / question 必填、code 可选 | thread_id / question / explanation JSON | graph + 已存在生成结果；业务和模型异常统一 HTTP 400 |

| SSE type | content                           | 时机                             |
| -------- | --------------------------------- | -------------------------------- |
| metadata | detectedLanguage、可选 confidence | 语言识别回调及最终结果，允许多次 |
| mermaid  | 当前完整图源字符串                | 0 到多次 partial + 最终快照      |
| mappings | NodeMapping[]                     | 完整生成成功后一次下发           |
| done     | 无                                | 成功结束                         |
| error    | 错误字符串                        | 失败结束；不再补 done            |

请求 schema 的 code 只校验 min(1)，未 trim，也未定义业务最大长度；浏览器对全空白输入的拦截并不约束直接调用 API 的客户端。

## 11. 差异与改进优先级

以下是代码证据支持的待办建议，本次未实施。

| 优先级 | 发现与证据                                                                | 影响与建议                                                                                                     |
| ------ | ------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| P1     | chain 抛错绕过 graph retry；`analyze-flow.node.ts` / `code-flow.graph.ts` | 结构错误和模型错误难以自纠错；将可重试异常转成节点错误状态，区分致命错误，并把校验反馈送入下一轮 Prompt        |
| P1     | Fetch 异常时 `generateFlow` 没有 catch/finally；只对 SSE error 更新状态   | 非 2xx、断网、JSON 错误可能让 UI 停在 streaming；统一收口失败状态并明确区分 done 与异常 EOF                    |
| P1     | `mermaidValidator.ts` 只检查前缀与箭头                                    | 无法保证 Mermaid 可渲染；使用实际解析器校验完整结果，并补映射双向集合检查                                      |
| P1     | code 修改不使旧结果失效；checkpoint 混合恢复新 code 与旧 result           | 定位/解释失真；保存生成代码版本或 hash，代码变化后要求重新生成或明确绑定旧快照                                 |
| P1     | checkpoint JSON 仍被 Git 跟踪                                             | 文件包含源码和模型结果，运行产生 diff；将运行时数据退出版本管理并定义保存/清理边界                             |
| P2     | 默认 provider=langchain，但追问 UI 不感知 provider                        | 用户生成成功后仍可能追问失败；选择统一默认能力或返回能力元数据让 UI 决定是否启用                               |
| P2     | `CODE2FLOW_MAX_RETRIES` 只进入 trace 配置，未进入 API graph state         | 观测与实际策略可能不一致；用同一配置解析结果驱动执行和记录                                                     |
| P2     | Axios timeout 10 秒；追问失败显示统一会话错误                             | 慢模型请求易超时且提示失真；合理配置 LLM 超时并显示明确原因                                                    |
| P2     | 文件缓存与队列仅在单实例内有效，写入直接覆盖原文件                        | 多实例/故障时状态不可靠；先明确单实例部署边界，再考虑原子写或数据库                                            |
| P2     | 无取消/心跳/断线恢复；SSE 未观察到请求关闭后取消模型                      | 连接中断仍可能继续生成；引入取消信号，并补流终止与故障回归测试                                                 |
| P2     | 前端 DTO 手写；单个 graph 测试间接覆盖少量归一化                          | 契约和交互容易漂移；补 Zod 边界、SSE 分帧/异常、mapping 与 HTTP 集成测试                                       |
| P2     | `vite.config.js` 和 `.ts` 同时存在                                        | 配置入口容易混淆；指定唯一来源，移除冗余前先确认当前工具解析入口                                               |
| P2     | createApp 只注册 JSON 和路由，cors 未使用                                 | 当前同源代理可用；若采用分域部署，应设计 API 地址与允许来源，不能直接照阶段文档部署即认为可用                  |
| P2     | `securityLevel: loose` + 模型生成的 Mermaid/HTML labels                   | 动态图源需要可信边界；保留点击功能时明确控制允许指令与标签，针对恶意图源做验证，静态阅读不能证明存在可利用漏洞 |
| P3     | follow-up 调用未统计同等 Token/轮次，历史 validationErrors 会覆盖         | trace 不能完整解释成本或每次重试原因；用调用级记录和追加式校验事件补齐                                         |
| P3     | `docs/architecture.md`、Prompt spec、旧分析报告滞后                       | 容易误认 StateGraph、历史聊天、完整语法校验及旧测试规模；按当前实现更新真源文档                                |

文档目标还包括 500ms 防抖、可拖动分栏、2–3 个 few-shot、最多 3 次重试；当前代码与这些目标有差距。生成 Prompt 只给一个结果形状示例，并非完整的 2–3 组输入/输出示例。Prompt 已改成通过工具提交结构化参数，和旧文档“直接输出严格 JSON”也应统一表述。
